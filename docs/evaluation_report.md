# Evaluation Report

All numbers below were **measured** by `evaluation/run_evaluation.py`, which runs the real pipeline (`run_job` + Gemini `gemini-2.5-flash`, temperature 0) on a labelled dataset and compares the output with the ground truth in `evaluation/dataset/labels.json`. Raw per-document output: `evaluation/results/results.json`. Summary: `evaluation/results/summary.md`.

## Dataset

21 **fabricated** files (no real data), generated by `evaluation/generate_dataset.py` with a fixed seed:

| Group | Files | Purpose |
|---|---|---|
| Digital PDFs | 12 (incl. 5 with injected flaws) | Varied date styles, leading-zero invoice numbers, no tax/due/currency, 8 line items |
| Scans (PNG) | 3 | Light, medium and heavy blur/rotation/noise |
| CSV / XLSX | 2 + 2 | Spreadsheet input |
| Corrupt / unsupported | 2 | Failure handling |

19 files have ground truth (the 2 broken files must fail safely). 5 contain deliberate mistakes (wrong total, wrong line amount, missing date, missing invoice number, duplicate).

## What went wrong (all of it)

All 5 wrong field values come from **one file**, `09_scan_heavy.png` (OCR misreads, not model invention):

| Field | Truth | Read as |
|---|---|---|
| invoice_number | INV-1009 | INV 1008 |
| invoice_date | 2026-05-16 | 2008-06-16 |
| customer_name | Delta Office Solutions | Dette Orion Sansone |
| subtotal | 104410.0 | 14410.0 |
| tax | 5220.5 | 220.5 |

The system did **not** accept these silently: `09` was flagged `low_ocr_confidence`, `total_mismatch` and `uncertain_field` and sent to human review.

Line items did not match in two scans: `08_scan_medium` (0 of 3 matched although every header field was correct) and `09_scan_heavy` (0 of 5, 4 predicted). For `08` the likely cause is small OCR differences in the descriptions, because the matcher requires an exact description match; this was not investigated further. The matching rule is therefore strict and may understate line-item quality.

## Run history (kept on purpose)

1. **Run 1** (`evaluation/results/run1_quota_limited_*`): files 18 and 19 failed with HTTP 429 because the Gemini free tier allows about 20 requests/day on this model. This run is **not** used for any number above.
2. **Final run**: after the quota reset, all 19 AI documents completed. Successful AI answers are cached in `evaluation/results/ai_cache.json`; re-running reproduces the same report without an API key.

## Limitations

- **Small, synthetic dataset** (21 files, 19 labelled). One file per scan quality level, so the scan numbers are anecdotal, not statistically reliable.
- Synthetic invoices are cleaner and more uniform than real ones; real-world accuracy will be lower.
- Strict exact-match line-item scoring; no partial credit.
- English-only OCR; only the invoice document type.
- Results depend on a pinned model (`gemini-2.5-flash`) and may change with other versions.
- Unit and API tests (64) check code correctness, not extraction quality; this report covers quality.

> Note: speed figures come from the live run. Re-running from the cache (as `summary.md` now shows) reproduces every accuracy number but reports near-zero time, because no Gemini call is made.
